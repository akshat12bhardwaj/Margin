# Software Requirements Specification: Margin

Course book exchange marketplace · CSE3005 Software Engineering · BML Munjal University

Version 1.0 · 6 November 2026 · Prepared by: Margin project team

Margin is an independent student project. It is not affiliated with or endorsed by BML Munjal University.

## 1. Introduction

### 1.1 Purpose

This document specifies the functional and non-functional requirements of Margin, the system implemented in this repository. It is the reference for the design document (docs/02-Software-Design), the test report (docs/04-Testing) and the requirements traceability matrix. Every requirement below describes behaviour that exists in the current code unless it is marked as not implemented.

### 1.2 Scope

Margin is a web application in which BMU students and faculty list used course books, find them by subject, semester and keyword, negotiate a price and arrange an in-person exchange. An administrator handles reports of fraudulent or misleading listings and misbehaving accounts.

In scope: accounts (email and password, optional Google sign-in), listings with photos, search and filtering, wishlists, purchase requests (Buy now and offers), negotiation, messaging, notifications, reporting, moderation, an administrator dashboard and audit log, and a removable set of example listings with automated sellers for demonstration.

Out of scope: online payment, delivery, verification of student or faculty status, email verification at registration, and native mobile apps.

### 1.4 Definitions

| Term | Meaning |
| --- | --- |
| Member | A registered student or faculty account that can buy and sell |
| Visitor | Anyone browsing without logging in |
| Listing | A book offered for sale (collection `books`) |
| Subject | One of 39 academic subjects in the shared catalogue `shared/subjects.mjs` |

### 1.5 System overview

The client is a React single-page application. It calls a REST API built with Express on Node.js, which stores data in MongoDB through Mongoose. Photos are stored on the server's disk, or in Cloudinary when it is configured. Google OAuth 2.0 and an SMTP server are optional external services. The architecture is shown in Figure 2.13 of the design document.

## 2. Problem statement

Course books at BMU are expensive when new and are often needed for one semester only. Students finishing a course usually have no reliable channel to pass books on: notices on group chats are lost quickly, give no way to search by subject or edition, and leave buyers unsure whether a book is still available or who else has already agreed to buy it. Faculty who hold older editions face the same problem. Exchanges also carry risk: misleading listings and unreliable sellers have no consequence when there is no record and no one to report them to.

## 3. Proposed solution

Margin gives the BMU community one place to list and find course books:

- Listings are categorised by a fixed subject catalogue and semester, so books for a course can be found by subject, keyword, ISBN or course code.
- A buyer either accepts the listed price (Buy now) or makes an offer. The seller accepts, declines or counters. Acceptance reserves the book for that buyer alone, which removes the "who gets it" uncertainty.
- Every negotiation and exchange is coordinated in an in-app chat tied to the book, and the seller confirms the exchange after meeting in person. No payment passes through the site.
- Members can report listings and users. An administrator reviews reports, hides or removes listings and suspends accounts, and every administrative action is recorded in an audit log.

## 4. Stakeholders and actors

| Actor | Description | Permissions (as implemented) |
| --- | --- | --- |
| Visitor | Not logged in | Browse, search, filter and view active, reserved and sold listings; view public profiles; register; log in; request a password reset |
| Student (buyer or seller) | Member with role `student`; optional programme and semester (1 to 8) | Everything a visitor can do, plus create, edit, deactivate and delete own listings; wishlist; Buy now and offers; respond to offers; message; confirm exchanges; cancel requests; report; notifications; edit profile and password |
| Faculty member (buyer or seller) | Member with role `faculty`; optional designation. Status is self-declared and shown as a label | Same as a student |
| Administrator | Role `admin`, created only with `npm run create-admin` | Dashboard statistics; review and decide reports; hide, remove and restore listings; suspend, deactivate and restore accounts; view the audit log. Cannot buy, sell, use Google sign-in or be moderated |
| Google Identity Service | External system | Authenticates members who choose Google sign-in |
| Email (SMTP) service | External system, optional | Delivers password reset links |

A suspended member can still log in and read, but cannot list, buy, message or report. A deactivated member cannot log in.

## 5. Functional requirements

Priorities use MoSCoW (Section 9). Source modules are listed in the traceability matrix.

### 5.1 Accounts

**FR-01 Registration (Must).** A visitor registers with name, email, password (8 to 72 bytes) and role (student or faculty). Students may add programme and semester (1 to 8); faculty may add a designation. The university is always BML Munjal University. A duplicate email is refused. Registration cannot create an administrator or set an account status.

**FR-02 Login and logout (Must).** A member logs in with email and password and receives a session cookie (JWT, httpOnly, 7 days). Wrong credentials return one generic message. Logout clears the cookie. Login, registration and password reset are rate limited per IP address.

**FR-03 Google sign-in (Should).** When configured, a visitor can sign in with Google. An existing account with the same email is linked on first use (its password is removed and older sessions end). A new user completes sign-up by choosing a role. Administrator and deactivated accounts cannot use Google sign-in, and a different Google identity cannot take over a linked account.

**FR-04 Password reset and change (Should).** A visitor requests a reset link by email. The response is the same whether or not the email exists. The link is single-use and expires after one hour, and using it ends older sessions. A logged-in member changes their password by entering the current one.

**FR-05 Profile management (Should).** A member edits name, programme, semester, designation and bio. Role and status cannot be changed this way. Public profiles show name, role, programme or designation, bio and active listings, never the email address.

### 5.2 Listings

**FR-06 Create listing (Must).** A member lists a book with title, author, optional ISBN (10 or 13 digits), subject, optional course, semester (1 to 8, optional), edition, publication year, description, condition (New, Like New, Good, Acceptable, Heavily Used), selling price (positive amount in rupees) and 1 to 6 photos (JPEG, PNG or WebP, 5 MB each). Files whose content does not match an image type are refused. A member can create at most 30 listings per hour.

**FR-07 Subject catalogue (Must).** The subject must be one of the 39 predefined subjects in four groups (Computer Science; Mathematics and Basic Sciences; Core Engineering; Other Academic Subjects). The server rejects any other value, including a manipulated request. The listing form offers the catalogue as a grouped selection list; free-text subjects are not possible.

**FR-08 Edit listing (Must).** Only the owner can edit a listing, and only while it is active or deactivated. Photos can be kept, removed or added (at least one must remain). Clearing an optional field removes it. A listing created before the subject catalogue must be given a catalogue subject when edited.

**FR-09 Deactivate, reactivate and delete listing (Must).** The owner can deactivate (hide from buyers) and reactivate an active or deactivated listing, or delete it. Deactivating or deleting cancels open requests on it, and deleting notifies members who saved it. Deleted listings stay readable to past buyers for their records.

### 5.3 Discovery

**FR-10 Browse and search (Must).** Anyone can browse active listings, 12 per page, sorted by newest, oldest, price (low to high, high to low) or publication year. A keyword matches title, author, subject, course or ISBN, ignoring case, spaces and hyphens in ISBNs.

**FR-11 Filters (Must).** Results can be filtered by subject, semester, course, edition, price range, condition (several at once) and seller role. Filters combine, are reflected in the page address so a filtered view can be shared or revisited, and can be cleared at once. The home page shows the eight subjects with the most listings, each opening the subject filter.

**FR-12 Listing details (Must).** The details page shows photos, all book facts, price, condition, status, seller name and role, and up to four related listings in the same subject. Reserved and sold listings remain visible with their status.

**FR-13 Wishlist (Should).** A member saves and removes listings. Saving is idempotent. Saved listings that are later sold or removed are shown as such.

### 5.4 Purchasing and negotiation

**FR-14 Buy now (Must).** On an available listing, a buyer chooses Buy now, sees a confirmation with the title and listed price, and confirms. This creates a purchase request at the full listed price, notifies the seller and opens the chat for that request. The book is not marked sold at this point.

**FR-15 Make an offer (Must).** From the chat, a buyer offers a whole-rupee amount from 0 up to the listed price.

**FR-16 Respond to an offer (Must).** While a request is pending, only the party who did not make the current offer can accept, decline or counter it. A counteroffer must differ from the current amount and not exceed the listed price. If the offer changed in the meantime the action is refused, so a stale screen cannot accept an outdated price.

**FR-17 Reservation and conflict prevention (Must).** Accepting a request reserves the listing. A buyer cannot request their own listing, cannot hold two open requests on one listing, and a listing can never have two accepted or completed requests, even under simultaneous accepts (enforced by the database).

**FR-18 Exchange coordination and completion (Must).** After acceptance the chat stays open for arranging place, date, time and payment in person, at the agreed price. Only the seller can confirm that the exchange took place ("Mark as sold"). This marks the listing sold, completes the request, cancels any other open requests and notifies the buyer. Completed and closed requests appear in each party's transaction history.

**FR-19 Cancel a request (Must).** Either party can cancel a pending or accepted request. Cancelling an accepted request returns the listing to available.

### 5.5 Communication

**FR-20 Messaging (Must).** A buyer can message the seller of a listing. Each conversation belongs to one listing and one buyer and is visible only to its two parties. Offers, counteroffers and decisions appear in the conversation as cards. Unread counts are kept for each side. Sending is limited to 30 messages per minute.

**FR-21 Notifications (Should).** Members are notified of requests, offers, decisions, messages, moderation actions, report outcomes and account changes, and can mark one or all as read.

### 5.6 Trust and moderation

**FR-22 Reporting (Must).** A member reports a listing or a user with a category (fake listing, incorrect edition, counterfeit or damaged, suspicious seller, scam or fraud, harassment, other) and a description. Self-reports and duplicate open reports are refused, example listings and fictional sellers cannot be reported, and a member can file at most 20 reports per hour. A reported listing is flagged for the administrator.

**FR-23 Report review (Must).** The administrator marks a report under review, then resolves (upholds) or rejects it with a recorded decision. A closed report cannot be changed. The reporter is told the outcome; the reported user is told only when a report is upheld.

**FR-24 Listing moderation (Must).** The administrator hides, removes or restores a listing with a reason. Hiding or removing cancels open requests and notifies the seller with the reason.

**FR-25 Account moderation (Must).** The administrator suspends, deactivates or restores an account with a reason. Suspension takes effect immediately and hides the member's listings; restoring brings them back. Deactivation ends sessions and blocks login. Administrator accounts cannot be moderated.

**FR-26 Dashboard and audit log (Should).** The administrator sees statistics for real members (example data reported separately), repeat-offender counts and a paginated audit log. Every administrative action records the administrator, action, target and reason.

### 5.7 Demonstration data

**FR-27 Example marketplace (Could).** A seed script adds fictional sellers and listings of real books taken from 17 BMU course handouts. Simulated listings are identified in the listing facts, seller profile and exchange records. Their sellers use addresses under `@demo.invalid`, cannot be logged into, and can be removed completely without touching real data. Seeding refuses production and non-local databases unless explicitly authorised.

**FR-28 Automated example sellers (Could).** A member can message and negotiate with a fictional seller through the normal chat. The seller replies from fixed rules: it accepts at 90% or more of the listed price, declines below 60%, otherwise counters halfway (never below 90%), and answers questions about availability, condition, edition and meeting. Three suggested messages fit the stage of the conversation; the text box remains available. Conversations between real members never receive automated replies.

### 5.8 Interface

**FR-29 Home page and appearance (Could).** The home page shows a rotating showcase of three recent covers (each opens its own listing), subject categories, and shelves of recent, affordable, faculty-listed and recently published books. Simulated-listing identification stays in the detail context. Members can switch between light and dark themes; the choice persists.

## 7. Constraints

- Technology: MongoDB, Express, React and Node.js (MERN). The current frontend toolchain requires Node.js 22.12 or later.
- Campus focus: every account and listing belongs to BML Munjal University.
- Exchanges happen in person. There is no payment gateway; prices are agreed in the app and paid when the book is handed over.
- Independent project, not affiliated with or endorsed by the university.
- Browser-based: a current desktop or mobile browser with JavaScript enabled.
- MongoDB runs as a standalone server, so multi-document transactions are not used; integrity relies on conditional updates and unique indexes.

## 8. Assumptions and dependencies

Assumptions:

- Members state their role honestly; faculty status is self-declared and labelled as such.
- Buyer and seller can meet on campus to exchange and pay.
- The administrator account is created by someone with access to the server.

## 10. Acceptance criteria

| Requirement | Acceptance criteria (all must hold) |
| --- | --- |
| FR-01 | Registration with valid data returns 201 and logs the user in; a duplicate email returns 409; role `admin` is refused; the stored password is a bcrypt hash |
| FR-02 | Correct credentials set an httpOnly cookie and open the dashboard; wrong credentials return 401 with a generic message; after the configured number of attempts further logins return 429 |
| FR-03 | A new Google user completes sign-up and can sign in again; an existing email is linked; admin, deactivated or mismatched identities are refused; a callback without matching state is rejected |
| FR-06, FR-07 | A listing with a catalogue subject, semester 1 to 8, positive price and 1 to 6 valid images is created; an unknown subject, price 0, semester 9 or a non-image file is refused with a field error |
| FR-08 | Only the owner can edit; the edited subject is stored; removing all photos is refused |
| FR-10, FR-11 | Keyword, subject, semester, course, edition, condition, price and seller-role filters return exactly the matching active listings, alone and combined; clearing filters restores all results |
| FR-13 | Saving twice keeps one entry; a sold or removed saved listing shows its status; removing works |
| FR-14 | Buy now shows the title and listed price before sending; the request is stored at the listed price as pending and the buyer lands in the chat; the listing is still available until the seller accepts |
| FR-15, FR-16 | Offer ₹400 on a ₹490 listing, counter ₹450, accept: the request is accepted at ₹450 with history pending → countered → accepted; a party cannot answer their own offer; a stale offer is refused with 409 |
| FR-17 | A second buyer cannot request a reserved listing; two simultaneous accepts produce exactly one winner; self-requests are refused |
| FR-18 | After acceptance both parties can still send messages; after "Mark as sold" the listing is sold, the request completed and the buyer notified |
| FR-20 | Only the two parties can read a conversation (others get 404); unread counts increase and reset when read |
| FR-22 to FR-25 | A report flags the listing; duplicate and self-reports are refused; resolving requires a decision and is final; hide/remove/restore and suspend/deactivate/restore take effect immediately, notify the affected member and create audit entries |
| FR-28 | A real member's offer to an automated seller is answered by the rules; the agreed price is stored; a real member's conversation with another real member receives no automated reply |
